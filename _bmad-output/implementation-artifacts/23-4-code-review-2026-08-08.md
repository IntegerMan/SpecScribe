## 2. Findings

Three findings, all from the orchestrator's own reading. This is not a substitute for the five layers.

### F1 — `splitContentRegion` cuts at the FIRST `</main>`, and nothing asserts there is only one — MEDIUM, patch

`web/ir/adapter.ts:260` computes the closing boundary as the *first* closer after the opener:

```ts
const mainClose = contentHtml.indexOf(MAIN_CLOSER, mainOpen)
...
mainInnerHtml: contentHtml.slice(openTagEnd + 1, mainClose),
trailingHtml:  contentHtml.slice(mainClose + MAIN_CLOSER.length),
```

`IrSurface.vue` then renders `trailingHtml` **outside** `<main>` — that is the whole point of the field, added
by this story's finding 4 to recover `deep-analytics.html`'s `:target` lightbox.

The C#-side invariant test that is supposed to make this safe checks only **openers**
(`tests/SpecScribe.Tests/SiteGeneratorSpaTests.cs:948–949`):

```csharp
Assert.Equal(1, CountOccurrences(html, mainMarker));   // "<main id=\"main-content\""
Assert.Equal(1, CountOccurrences(html, "<main"));      // note: does NOT match "</main"
```

**Nothing anywhere counts `</main>`.** So a page body carrying a second, stray `</main>` — an unescaped code
sample, a doc page quoting markup, a future templater emitting nested structure — passes every C# gate, and
then `splitContentRegion` truncates `mainInnerHtml` at that stray closer and relocates *the remainder of the
real page body* into `trailingHtml`, i.e. **outside the `<main>` landmark**, with a stray `</main>` left in the
output.

Failure scenario: a templater emits `…<pre>&lt;/main&gt;</pre>…` correctly escaped today; anything that stops
escaping it, or any body that legitimately contains the literal, silently moves content out of the landmark.
This is exactly the class of defect the story's own finding 4 documents — content relocated across the
landmark boundary, invisible to `measure:parity` (which compares `<main>` only), to `check:links`, and to
`check:a11y`.

**Fix (unambiguous):** assert the closer count alongside the opener count in
`EveryIrRegion_HasOneBalancedWayfindingBand_AndExactlyOneMainLandmark` — `Assert.Equal(1,
CountOccurrences(html, "</main>"))`. That makes the ambiguity impossible at the emitter rather than guessing
differently at the consumer. Switching the TS side to `lastIndexOf` is **not** the fix: it merely moves which
stray closer wins, and it would corrupt the `trailingHtml` case this story exists to support.

### F2 — `enforce()` throws before logging, so a fatal violation discards every warning — LOW, patch

`web/ir/contracts.ts:87–91`:

```ts
export function enforce(violations: ContractViolation[]): void {
  const fatal = violations.find((v) => v.severity === 'error')
  if (fatal) throw new Error(fatal.message)
  for (const v of violations) console.warn(`[specscribe] ${v.message}`)
}
```

The `console.warn` loop is unreachable whenever any `error` is present, so the build fails with exactly one
message and the accompanying warnings — the context that would explain *why* — are silently dropped. Also
only the first error is surfaced if several ever coexist.

**Fix:** emit the warnings first, then throw. One-line reordering, no behaviour change to the fatal path.

### F3 — `bodyStart` scans for the breadcrumb marker from index 0 — LOW, defer

`web/ir/adapter.ts:268–272` takes `indexOf(CRUMB_MARKER)` over the whole region and then filters
`< mainOpen`. Any `<div class="breadcrumb"` appearing inside the **nav** markup — before the real wayfinding
band — becomes `bodyStart`, silently reclassifying nav content as wayfinding.

Not currently reachable (no nav shape emits that class) and the C#-side test mirrors the identical logic, so
both sides agree and no gate would catch a divergence. Recorded as pre-existing structural fragility inherited
from Story 22.4's split rule rather than introduced here.

### Considered and NOT reported

- **`dashboardContract` early-returns before the fatal ADR 0013 twin check when `needsHierarchyEngine` is
  false** (`web/ir/contracts.ts:50–65`). This means the file's only `error`-severity contract cannot fire when
  a chart's loss also clears the flag. It is deliberate, documented in place, and is precisely owner decision
  **D6** — a chart-less dashboard must not fail another project's build (the CORA 32/33 route). Accepted risk,
  not a defect.
- **`resolveFamily`'s `pass-through` fallback** (`web/ir/families.ts:137`) is guarded by a completeness gate
  that asserts the real manifest leaves `pass-through` empty, which is the right shape — a hand-written
  fixture would only prove the table matches itself.
